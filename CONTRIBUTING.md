# Contributing to Deckhand

Deckhand is at Phase 0: specification. There is no application to build or
run yet. That makes this a good time to contribute, because the cheapest bug
to fix is one that is still just a sentence in a document.

## Where to start

The most valuable contributions right now are to the specification, not
code. In rough order of usefulness:

1. Review [`docs/CONTROL_MAPPING.md`](docs/CONTROL_MAPPING.md) and challenge
   anything that seems ambiguous, contradictory, or hard to operate with a
   pointer alone.
2. Read [`docs/ADAPTER_PROTOCOL.md`](docs/ADAPTER_PROTOCOL.md) and try to
   find a gap: a status transition it cannot express, or a capability it
   assumes an adapter has but might not.
3. Give accessibility feedback, especially if you use a pointer device other
   than a standard mouse, or rely on switch access, eye tracking, or a
   trackball. Use the accessibility feedback issue template.
4. Try to break [`docs/SECURITY_MODEL.md`](docs/SECURITY_MODEL.md). The
   approve and deny buttons are a security surface. If you can describe a
   way the surface could approve something the user did not mean to
   approve, that is a serious and welcome finding.
5. Once there is code, pick up a small, clearly scoped issue rather than
   proposing a new subsystem unprompted.

## Ways to contribute

### 📐 Specification

Open an issue or a pull request against any file in `docs/`. Specification
pull requests are reviewed the same as code would be: clarity and
consistency matter, not just correctness.

### 💻 Implementation

There is no implementation yet (Phase 0). Once Phase 1 starts, implementation
work will be scoped and tracked in `TODO.md`. Please open an issue before
starting a large, unsolicited implementation, so the approach can be agreed
first.

### ♿ Accessibility

Deckhand exists because navigating several terminal windows at once is
expensive for some people. Accessibility feedback is not a secondary
concern here, it is close to the whole point. See the section below and
`docs/ACCESSIBILITY.md`.

### 📖 Docs

Fix unclear wording, broken links, and inconsistencies between documents.
See [`docs/WORKFLOW.md`](docs/WORKFLOW.md) for which document is
authoritative for which fact, so a fix lands in the right place instead of
being duplicated in two places that can drift apart again.

### 🧪 Testing

Once there is code to test, this section will describe how to run the test
suite. For now, the most useful form of testing is reading the adapter and
security specs and trying to find a real scenario they do not cover.

## Getting started

1. Clone the repository.

   ```powershell
   git clone https://github.com/owenpkent/deckhand.git
   cd deckhand
   ```

2. There is nothing to install or build yet. Phase 0 is documentation only,
   so open the docs in an editor and start reading from `README.md`.

3. Ready to propose a change? See Conventions below for commit and branch
   naming, then Pull requests for how to submit it.

## Conventions

**Commit messages** follow [Conventional
Commits](https://www.conventionalcommits.org/), lowercase subject, no
trailing full stop:

```
feat: add dial commit-target behaviour
fix: correct amber status transition
docs: clarify adapter capability list
chore: update repository scaffolding
refactor: simplify tile state description
```

Scope when it helps: `feat(dial):`, `fix(security-model):`.

**Branch names** use a `type/short-description` shape:

```
feature/dial-commit-targets
fix/amber-transition-race
docs/adapter-protocol-clarify
```

**No AI attribution.** Do not add `Co-Authored-By: Claude`, `Generated by`,
or any similar AI attribution trailer to commits or pull request
descriptions, regardless of what tooling helped write them. This is a firm
rule for this repository.

**Documentation style:**

- No em dashes and no en dashes, anywhere. Use a comma, a colon,
  parentheses, or a full stop instead.
- Wrap prose at roughly 80 columns.
- Plain, honest tone. No marketing language. Hedge where something is
  unproven or undecided, rather than asserting confidence the project does
  not have.
- Never state that something is built or working unless it demonstrably is.
  While the project is at Phase 0, that means almost nothing should be
  described in the present tense as functioning.

## Pull requests

Use the [pull request template](.github/PULL_REQUEST_TEMPLATE.md); it is
applied automatically when you open a PR. It includes an accessibility
check and a sync checklist.

The sync checklist matters more than it looks. Deckhand's specification is
spread across several documents that describe the same system from
different angles (control behaviour, adapter contract, security model, and
so on). If your change touches more than one of these, the change
propagation table in [`docs/WORKFLOW.md`](docs/WORKFLOW.md) says which
other files need updating in the same pull request. Please check it before
requesting review.

## Accessibility considerations

Deckhand's mouse-only rule is not a feature, it is the entire premise, and
it applies to contributions too:

- Every feature must be fully operable with a pointer alone. If a design
  only works with a keyboard shortcut or a held key combination, it is not
  finished.
- Keyboard and voice input are conveniences layered on top. They are never
  requirements for using any part of the surface.
- Hit targets have a minimum size (see `docs/UI_SPEC.md` for the current
  figure). Do not propose a control smaller than that minimum, even for a
  secondary action.

If you are not sure whether a proposed design meets this bar, say so in the
pull request rather than guessing. That is useful information on its own.
